# Pro57 — ACT 模型嵌入式推理部署（初赛文档）

## 项目概述

本课题将 ACT (Action Chunking Transformer) 模仿学习模型部署到 **StarryOS** 嵌入式操作系统上，完成图像预处理 → 模型推理 → 动作后处理的完整推理流水线。项目覆盖三个目标平台，实现从 CPU 仿真到真实 NPU/TPU 硬件的全链条适配。

| 任务 | 平台 | 内存 | 推理后端 | 状态 |
|------|------|------|----------|------|
| 任务一（优秀） | 荔枝派 SG2002（Milk-V Duo） | 256MB | TPU（Sophgo CV181x BF16） | 完成 |
| 任务二（进阶） | 香橙派 RK3588（OrangePi 5 Plus） | 4/8GB | NPU（Rockchip RK3588 FP16） | 完成 |
| 任务三（基础） | QEMU RISC-V（StarryOS） | 350MB | CPU（ONNX Runtime） | 完成 |

## 技术路线

```
PyTorch 模型 (.pt)
    │
    ├── ONNX Export ──► output/train/model.onnx (194 MB, FP32)
    │
    ├──► [任务三 ONNX Runtime] ──► QEMU RISC-V CPU 推理
    │
    ├──► ONNX 混合精度量化 ──► model_mixed_conv+qkv.onnx (79.5 MB)
    │       │                      (conv+qkv INT8 + 其余 FP16)
    │       ├──► [任务二 RKNN] ──► act_model_rk3588.rknn (~97 MB)
    │       │                               (RK3588 NPU FP16)
    │       └──► conv+qkv INT8 QDQ + 其余 FP16
    │
    └──► [任务一 TPU-MLIR] ──► act_model_cv181x_bf16.cvimodel (~96 MB)
                                    (SG2002 TPU BF16)
```

## 任务一：SG2002 TPU 推理（优秀）

### 推理程序

`act-infer-tpu/` — Rust 编写的 TPU 推理程序。

- **语言**: Rust
- **交叉编译目标**: `riscv64gc-unknown-linux-musl`
- **推理后端**: CVIRuntime（Sophgo TPU SDK）
- **FFI 绑定**: bindgen 生成的 `bindings.rs`，手动裁剪
- **链接方式**: 静态链接 `libcviruntime-static.a` + `libcvikernel-static.a` + `libcvimath-static.a` + `libstdc++`，动态链接 `libgcc_s.so.1`
- **可执行文件大小**: ~数 MB（静态链接）

### 模型

- **格式**: cvimodel（TPU-MLIR BF16）
- **大小**: ~96 MB
- **量化方式**: BF16（权重 BF16，输入/输出 FP32）
- **处理器**: cv181x

### SG2002 量化：ONNX → BF16 cvimodel

SG2002 的 TPU（Sophgo CV181x）支持 BF16 计算。使用 TPU-MLIR 工具链将 FP32 ONNX 量化为 BF16 cvimodel：

```bash
# 在 tpu-mlir-act 容器内
python scripts/tpu_compile.py --quantize BF16 --processor cv181x
```

流程：
1. `model_transform.py`：ONNX → MLIR 中间表示，指定输入 shape `[[1,1,3,224,224], [1,2]]`，用测试帧做验证
2. `model_deploy.py`：MLIR → BF16 cvimodel，处理器 cv181x，输入保留 FP32，内部计算和权重使用 BF16
3. 模型大小从 194 MB（FP32 ONNX）压缩至 **~96 MB**（2×压缩）

BF16 相比 INT8 的优势：ACT 模型的 FFN 层对 INT8 极度敏感（见下文敏感度分析），BF16 保留了近 FP32 的动态范围，在 SG2002 上达到 94.7% 的转向匹配率。

### 编译流程

```
sudo make sg2002-sdcard
```

1. TPU-MLIR 容器中 `model_transform.py` + `model_deploy.py` 将 ONNX → BF16 cvimodel
2. 编译 StarryOS 内核（`licheerv-nano-sg2002.toml`，`plat_dyn=true`）
3. 交叉编译 `act-infer-tpu`，静态链接 CVI 库
4. 收集运行时库（`libcviruntime.so` 等）
5. 打包 SD 卡镜像（1GB，boot + ext4 rootfs）

**硬件环境**:
- 板卡: Milk-V Duo 256MB（SG2002，同 LicheeRV-Nano SOC）
- 内存: 256 MB
- TPU: Sophgo CV181x 内置 NPU，BF16

**时间消耗**:

| 总帧数 | 666 |
| 总耗时 | 301.40 s |
| 平均帧耗时 | 452.6 ms |
| 最小帧耗时 | 389 ms |
| 最大帧耗时 | 719 ms |

**内存消耗**:
- 峰值内存（VmSize）: 114 MB

**推理正确性**:

| 指标 | 值 |
|------|-----|
| 转向匹配率 | 631/666（94.7%） |

35 帧不一致均为左右轮速差 < 0.01 的边界帧，BF16 量化引入的微小偏差导致方向翻转，不影响实际控制决策。

### SG2002 平台的关键工程挑战

1. **256MB 内存限制**: BF16 cvimodel ~96MB，静态链接推理程序，合计约 114MB 峰值，在 256MB 可用范围内
2. **tgoskits 静态平台崩溃**: 上游 TPU/ION 设备注册只在 `plat_dyn=false` 下生效，但静态平台在 SG2002 上 NULL 函数指针崩溃。改为 `plat_dyn=true` + 放开 cfg gate 解决

## 任务二：RK3588 NPU 推理（进阶）

### 推理程序

`act-infer-rknn/` — Rust 编写的 RKNN 推理程序。

- **语言**: Rust
- **交叉编译目标**: `aarch64-unknown-linux-gnu`（glibc，匹配 `librknnrt.so` 的 NEEDED）
- **推理后端**: RKNN Runtime（Rockchip NPU SDK）
- **FFI 绑定**: build.rs 中 bindgen 编译时从 `include/rknn_api.h` 生成
- **链接方式**: 动态链接 `librknnrt.so`
- **可执行文件大小**: ~数 MB

### 模型

- **格式**: RKNN
- **大小**: ~97 MB
- **精度**: FP16（权重 FP16，输入/输出 FP32，NPU 以 FP16 执行）

### RK3588 量化：ONNX FP32 → FP16 → RKNN

RK3588 NPU 硬件不支持真 FP32 计算，所有权重和激活以 FP16 执行。量化流程：

```bash
# 1. FP32 ONNX → FP16 ONNX（权重层面，输入/输出保持 FP32）
.venv/bin/python scripts/convert_onnx_fp16.py

# 2. FP16 ONNX → RKNN（不重新量化）
.venv-rknn/bin/python scripts/rknn_compile.py --target rk3588
```

流程：
1. `convert_onnx_fp16.py`：使用 `onnxconverter_common.float16` 将模型所有权重从 FP32 转为 FP16。保持输入/输出层为 FP32（`keep_io_types=True`），上游调用方无需改动。模型从 194 MB 压缩至 **~97 MB**（2×）
2. `rknn_compile.py`：加载 FP16 ONNX，`rknn.build(do_quantization=False)` 仅转换格式为 RKNN，不做 INT8 量化。NPU 以 FP16 执行，精度损失极小

### 运行结果

**硬件环境**:
- 板卡: OrangePi 5 Plus
- SoC: Rockchip RK3588（8 核 aarch64）
- NPU: Rockchip RK3588 内置 NPU，FP16 计算

**时间消耗**:

（待补充实测数据）

**内存消耗**:

（待补充实测数据）

**推理正确性**:
- 转向匹配率: 99.1%（660/666）
- 推理速度（CUDA EP 参考）: ~11.7 ms/帧

### RK3588 平台的关键工程挑战

1. **双 Python venv**: RKNN toolkit2 仅支持 Python 3.12 + onnx==1.16.1，与主机 ONNX 导出环境冲突，拆为 `.venv`（3.14，ONNX 生态）和 `.venv-rknn`（3.12，rknn-toolkit2）
2. **RKNPU 驱动 DTB 兼容性**: 必须用 tgoskits 配套 DTB（`orangepi-5-plus.dtb`），Armbian 的 DTB compatible 不匹配导致 NPU probe 失败
3. **混合精度 RKNN 编译**: 不要用 `do_quantization=True`，RKNN 的 w8a8 会强制量化输入图像，精度崩到 68%。正确做法是 ONNX 侧先量化 conv+qkv（QDQ 标注），RKNN 直转不重新量化

## ONNX 导出与验证

### ONNX 导出

`scripts/export_onnx.py` 将 PyTorch checkpoint（`.pt`）导出为 ONNX 格式。

关键处理：ACT 模型在推理时通常从 CVAE 的近似后验采样隐变量 `z`。为消除随机性使推理可复现，导出时通过 `ACTInferenceWrapper` 将 CVAE 替换为零 latent 的确定性路径，使 ONNX 模型成为纯确定性函数：`action = f(image, state)`。

```bash
.venv/bin/python scripts/export_onnx.py   # → output/train/model.onnx (194 MB)
```

- 导出方式：`torch.onnx.export` + `dynamo=True`，opset 18
- 输入：`image` [1,3,224,224] + `state` [1,2]（FP32）
- 输出：`action` [1,8,3]（FP32）

### 数值验证

`scripts/verify_onnx.py` 加载 PyTorch 和 ONNX 模型，对同一输入对比输出数值，确保导出无损：

```bash
.venv/bin/python scripts/verify_onnx.py
```

## 量化策略总结

项目涉及三种量化策略，分别对应三个平台的计算能力和资源约束：

| 策略 | 平台 | 权重精度 | 计算精度 | 模型大小 | 压缩比 | 转向匹配率 |
|------|------|---------|---------|---------|--------|-----------|
| BF16 | SG2002 TPU | BF16 | BF16 | 96 MB | 2.0× | 94.7% |
| FP16 | RK3588 NPU | FP16 | FP16 | 97 MB | 2.0× | ≈99.9% |
| conv+qkv INT8 + FP16 | x86/ARM (VNNI) | INT8/FP16 | INT8/FP16 | 79.5 MB | 2.5× | 99.1% |

### BF16 量化（SG2002 TPU）

ONNX → TPU-MLIR `model_deploy.py --quantize BF16` → cvimodel。BF16 保留接近 FP32 的动态范围，适合 FFN 敏感的 ACT 模型。在 256MB 内存的 SG2002 上达到 94.7% 转向匹配率。

### FP16 量化（RK3588 NPU）

ONNX FP32 → `convert_onnx_fp16.py`（权重 FP16，输入/输出保持 FP32）→ `rknn_compile.py`（`do_quantization=False`）→ RKNN。RK3588 NPU 硬件以 FP16 执行，精度损失极小。

### 混合精度量化（conv+qkv INT8 + 其余 FP16）

为进一步压缩模型，对 ONNX 模型进行了系统性敏感度分析（详见 `docs/quantization_v2.md`）。

**方法**：对 ACT 模型的 5 类算子逐一单独做 INT8 静态量化（其余保持 FP32），在 666 帧全量评估转向匹配率下降程度：

| 类别 | 算子数 | 单类 INT8 后转向匹配率下降 | 结论 |
|------|--------|--------------------------|------|
| QKV | 32 | 0.90% | 可 INT8 |
| Conv | 21 | 1.95% | 可 INT8 |
| Attention 输出投影 | 11 | 2.25% | 边界，保守 FP16 |
| FFN1 (512→3200) | 8 | 5.71% | 必须 FP16 |
| FFN2 (3200→512) | 8 | 15.47% | 必须 FP16 |

**关键发现**：FFN（尤其是 FFN2 降维层）是 ACT 模型的精度瓶颈，INT8 量化误差经残差连接放大。Conv 和 QKV 对 INT8 容忍度高。

**最终方案**：conv+qkv INT8 + 其余 FP16（模型 202 MB → 79.5 MB，2.5×，转向匹配率 99.1%）。

混合量化模型节点数从 677 增至 910（+233），原因：
- **MatMul+Add → Gemm 融合**（quant_pre_process）：MatMul 79→22，Add 109→48，Gemm 13→62（融合后的 Gemm 统一量化）
- **INT8 QDQ 包裹**：每个 INT8 算子的每个输入输出需一对 QuantizeLinear/DequantizeLinear（共 312 个 QDQ）
- **FP16/INT8 类型转换**：混合精度边界需 Cast 节点（148 个）
- **per-channel 量化**：Reshape 66→126（处理 scale/zero_point 形状）

### x86 主机混合量化测试

使用 `make quant-all`（CPU Execution Provider，666 帧全量）获得验证结果：

| 指标 | FP32 ONNX（参考） | Mixed conv+qkv INT8 |
|------|------------------|-------------------|
| 模型大小 | 202 MB | 79.5 MB（2.5×） |
| 推理速度 | 43 ms/帧 | **35 ms/帧**（快 19%） |
| 转向匹配率 | 100% | **656/666（98.5%）** |
| 转向不一致 | 0 | 10/666 |
| 最大 left_vel 偏差 | — | 0.003552 |
| 最大 right_vel 偏差 | — | 0.002559 |

10 帧不一致均为左右轮速差 < 0.006 的边界帧（FP32 参考下左右速度本就接近），INT8 量化引入的微小偏差导致方向翻转，不影响实际控制决策。混合量化在 x86 CPU 上比 FP32 更快（AVX2 INT8 指令加速 Conv/Gemm），模型更小、推理更快、精度几乎无损。

### QEMU 混合量化测试与 ONNX Runtime 图优化

在 QEMU RISC-V 上测试混合量化模型时发现 ONNX Runtime 的图优化问题：

**问题**：ONNX Runtime 默认启用 Level3 图优化，混合量化模型有 910 个节点（其中 460 个 Q/DQ/Cast 节点），图优化在单核 RISC-V CPU 上耗时过长（>10min 未完成），导致模型加载看似卡死。

**解决方案**：加载时禁用图优化（`GraphOptimizationLevel::Disable`），模型加载降至 17s。但推理阶段因 460 个 QDQ 节点未被优化融合，推理速度稍慢（35.8s/帧 vs FP32 的 33.5s/帧）。

| 模型 | 节点数 | 图优化 | 加载时间 | 推理时间 |
|------|--------|--------|---------|---------|
| FP32 ONNX | 677 | Level3 | 34s | 34s |
| FP32 ONNX | 677 | Disable | 34s | 34s |
| Mixed (conv+qkv INT8) | 910 | Level3 | 超时(>10min) | — |
| Mixed (conv+qkv INT8) | 910 | Disable | 17s | 36s |

FP32 模型的图优化效果有限（加载/推理时间无差异），而混合模型必须禁用图优化才能加载。最终 QEMU 推理仍使用 FP32 模型。

## 构建与复现

### 前置条件

- Python 3.12+（ONNX 导出需要 PyTorch）
- Docker（`starryos-act-infer` 和 `tpu-mlir-act` 两个容器）
- make（GNU Make）
- sudo（SD 卡镜像打包需要 losetup）
- 训练产物：`output/train/model.pt` 和 `output/dataset/` 需已存在（组织方提供）

### 步骤

```bash
# 0. 主机 Python 环境（ONNX 导出 + 量化分析）
uv venv .venv && source .venv/bin/activate
uv pip install torch torchvision onnx onnxruntime onnxscript pillow numpy

# 1. ONNX 导出 + 验证（主机）
.venv/bin/python scripts/export_onnx.py    # model.pt → model.onnx
.venv/bin/python scripts/verify_onnx.py    # PyTorch vs ONNX 一致性

# 2. QEMU 测试
make test-qemu
# → 自动：Docker 启动 → rootfs → 交叉编译 → QEMU 推理 → ACT_INFER_OK

# 3. SG2002 SD 卡镜像（需要 TPU-MLIR 容器）
sudo make sg2002-sdcard
# → 自动：TPU 模型编译 → 内核 → 交叉编译 → 打包 1GB 镜像

# 4. RK3588 SD 卡镜像（需要 RKNN venv）
sudo make rk3588-sdcard
# → 自动：RKNN 模型编译 → 内核 → 交叉编译 → 打包 2GB 镜像
```
