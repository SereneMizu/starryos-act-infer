# RK3588 (OrangePi 5 Plus)

## 硬件

- SoC: Rockchip RK3588 (aarch64, 8 核)
- 板卡: OrangePi 5 Plus
- 串口: `/dev/ttyS7`，波特率 1500000

## 构建命令

```bash
make build-rk3588       # 只编译内核 → output/rk3588/starryos.uimg
make model-rk3588-fp16  # ONNX→RKNN FP16 模型编译(主机 .venv-rknn)
sudo make rk3588-sdcard # 编译内核 + 推理程序 + 打包 SD 卡镜像 → output/rk3588/rk3588-sdcard.img
```

需要 `sudo` 因为脚本内部使用 `losetup` 创建 loop 设备。

## Python 环境（双 venv）

RKNN 模型编译与 ONNX 导出/ORT 推理用的依赖冲突（`rknn-toolkit2 2.3.2` 代码用了 `onnx.mapping`，onnx 1.16 起移除），故拆两个 venv：

| venv | Python | 用途 | 主要依赖 |
|------|--------|------|----------|
| `.venv` | 3.14 | ONNX 导出 / ORT 推理 / verify | torch(新版)/onnx(新版)/onnxruntime/onnxscript |
| `.venv-rknn` | 3.12 | RKNN 模型编译（`rknn_compile.py`） | rknn-toolkit2==2.3.2 / **onnx==1.16.1** / numpy==1.26.4 / torch==2.4.0 CPU |

rknn-toolkit2 只有 cp312 wheel（无 cp314）；且必须钉 `onnx==1.16.1`（含 `onnx.mapping`）。详见 `requirements-rknn.txt`。Makefile 里 `RKNN_PYTHON := .venv-rknn/bin/python`，其余脚本仍用 `.venv/bin/python`。

```bash
# 建库（torch 用 CPU index，避免拉入 ~2GB 的 nvidia CUDA 包）
uv venv --python 3.12 .venv-rknn
uv pip install --python .venv-rknn/bin/python --index-url https://download.pytorch.org/whl/cpu torch==2.4.0
uv pip install --python .venv-rknn/bin/python -r requirements-rknn.txt
sudo apt install libgl1 libglib2.0-0   # opencv-python 运行需要 libGL.so.1
```

## ACT 推理部署（RKNN）

整体流程：

```
ACT PyTorch 模型 → ONNX → RKNN (rknn-toolkit2, 不量化) → StarryOS + RKNN 推理程序
```

### 推理后端

- **运行时库**: `librknnrt.so`（aarch64 glibc，来自 [rknn-toolkit2/rknpu2/runtime](https://github.com/airockchip/rknn-toolkit2/tree/master/rknpu2/runtime/Linux/librknn_api/aarch64)），存于 `starry-apps/act-infer-rknn/lib/`
- **头文件**: `rknn_api.h`，存于 `act-infer-rknn/include/`，由 `build.rs` 编译时 bindgen 生成 FFI 绑定
- **Rust 程序**: `act-infer-rknn`（`cargo new` 创建，依赖走 cargo，bindgen 作 build-dependency）

### 交叉编译目标：aarch64-unknown-linux-gnu（glibc）

`librknnrt.so` 的 NEEDED 依赖全是 glibc（`libc.so.6`/`libstdc++.so.6`/`libm.so.6`/`libpthread.so.0`/`libdl.so.2`/`libgcc_s.so.1`）。musl 与 glibc 不能在同进程中混链，因此 RKNN 程序交叉编译到 **`aarch64-unknown-linux-gnu`**（与 Debian rootfs 一致），而非 musl。容器需 `apt install gcc-aarch64-linux-gnu`（已加入 `make docker-up`）。

### 模型精度

RK3588 NPU 硬件不支持真 fp32 计算；`rknn_compile.py` 默认 `do_quantization=False`，权重保持浮点，NPU 以 **fp16** 执行——这是"不量化"能达到的最高精度。

### 混合精度 (enc_full: encoder 全 INT8 + decoder qkv INT8 + 其余 FP16)

**正确做法**：host 已量化的混合精度 ONNX (`model_mixed_enc_full.onnx`) 直转 RKNN，`do_quantization=False` 只转格式。RKNN 识别 ONNX 的 QDQ 标注，保留 enc_full 策略的 INT8 + FP16 分布，输入维持 float32，精度 100%（simulator 验证 50/50）。

```bash
make model-onnx-mixed    # 生成混合精度 ONNX (host, enc_full: encoder 全 INT8 + decoder qkv INT8 + 其余 FP16)
make model-rk3588-mixed  # ONNX 直转 RKNN (.venv-rknn, 不重新量化)
```

产物 `output/rknn/act_model_rk3588_mixed.rknn`（67MB）。推理程序 `act-infer-rknn` 无需改动（输入接口仍 float32）。脚本 `scripts/rknn_compile.py`，config 用 `optimization_level=2`（关闭影响精度的优化 pass）。

**关键教训（不要重新量化本模型）**：绝对不要用 `do_quantization=True`（w8a8 / auto_hybrid）。RKNN 的 w8a8 会把输入 images 也强制 int8 量化，而本模型 action 输出的 `left_vel/right_vel` 差异仅 ~0.001 量级，INT8 量化噪声 ~0.02 量级直接淹没 turn 方向判断，精度崩到 **68%**。穷尽验证：w8a16（权重8激活16）rk3588 不支持；手动 `hybrid_quantization_step1/step2` 在 2.3.2 有 pickle bug（旧接口退化）；`build(auto_hybrid=True)` 仍 68%（输入仍被 int8）。唯一可行路径是直转已量化的 ONNX。

### bindgen 编译时生成

`act-infer-rknn/build.rs` 在编译时从 `include/rknn_api.h` 用 bindgen 生成绑定到 `OUT_DIR/bindings.rs`，`main.rs` 通过 `include!(concat!(env!("OUT_DIR"), "/bindings.rs"))` 引入。生成风格与 `act-infer-tpu` 一致（`#[repr(u32)]` Rust 枚举 + allowlist 裁剪）。

### 板上运行

rootfs 内（`rk3588-sdcard` 自动安装）：

| 路径 | 内容 |
|------|------|
| `/usr/bin/act-infer-rknn` | Rust 推理程序（aarch64 glibc） |
| `/lib/librknnrt.so` | RKNN 运行时库 |
| `/opt/act-infer/model.rknn` | 编译后的 RKNN 模型 |
| `/opt/act-infer/{stats.json,frames,reference.json,infer.sh}` | 归一化参数/图像帧/参考结果/运行脚本 |

```sh
/opt/act-infer/infer.sh
```

## 前置准备：提取引导链

SD 卡镜像依赖 Rockchip 引导链（RKNS + SPL + ATF + U-Boot），需从 Armbian 官方镜像提取：

```bash
# 下载 Armbian 镜像（首次）
# https://github.com/orangepi-xunlong/orangepi-build/releases

# 提取前 16MB（扇区 0~32767）作为引导链
dd if=<armbian.img> of=output/rk3588/rk3588-bootchain.img bs=512 count=32768
```

Armbian 镜像分区布局（GPT）：

| 区域 | 扇区 | 内容 |
|------|------|------|
| 引导链 | 0 ~ 32767 | RKNS + SPL + ATF + U-Boot（16MB） |
| rootfs | 32768 起 | Linux root (ARM-64) |

## SD 卡镜像布局

`output/rk3588/rk3588-sdcard.img`（2GB）：

- 扇区 0~33: Protective MBR + GPT 头（由 `sfdisk` 写入）
- 扇区 34~32767: Rockchip 引导数据（SPL/ATF/U-Boot，从 bootchain dd 写入，跳过 GPT 头）
- 扇区 32768 起: ext4 rootfs（Alpine minirootfs aarch64 + `/starryos.uimg`）

## U-Boot 手动启动

写入 SD 卡后，在 U-Boot 命令行执行：

```bash
ext4load mmc 1:1 ${kernel_addr_r} /starryos.uimg
ext4load mmc 1:1 ${fdt_addr_r} /orangepi-5-plus.dtb
bootm ${kernel_addr_r} - ${fdt_addr_r}
```

- `${kernel_addr_r}` = `0x02000000`（U-Boot 环境变量）
- `${fdtcontroladdr}` = U-Boot 内置 DTB 地址，通过 x0 传给内核
- 内核入口：`kernel_entry(_fdt_addr: usize)` 从 x0 读 DTB

## 设备树（DTB）—— 必须用 tgoskits 自带的

**关键**：rootfs 里的 DTB 必须用 `tgoskits/os/StarryOS/configs/board/orangepi-5-plus.dtb`，**不能用 Armbian 的** `sdboot/rk3588-orangepi-5-plus.dtb`。`build-rk3588-sdcard.sh` 已默认安装 tgoskits 版（文件名 `orangepi-5-plus.dtb`）。

原因——内核 RKNPU 驱动（`drivers/ax-driver/src/rknpu.rs`）按 compatible 匹配设备：

| DTB 来源 | NPU 节点 compatible | NPU 节点结构 | 驱动是否匹配 |
|----------|--------------------|--------------|--------------|
| tgoskits `orangepi-5-plus.dtb` | `rockchip,rk3588-rknpu` | 单节点 `npu@fdab0000` + 3 reg（每核一块） | ✅ 匹配 |
| Armbian `rk3588-orangepi-5-plus.dtb` | `rockchip,rk3588-rknn-core` | 3 个独立节点（每核一个，pc/cna/core 子区域） | ❌ 不匹配 |

用错 DTB 时 NPU probe 不触发 → 没有 `/dev/rknpu` → librknnrt 查版本失败 → `Meet unsupported target type: 0xffffffff` → 空指针解引用段错误（详见"故障排查"）。

## Board 配置

### 构建配置

`tgoskits/os/StarryOS/configs/board/orangepi-5-plus.toml`:

- `target = "aarch64-unknown-none-softfloat"`
- `env = { UIMAGE = "y" }`（启用 mkimage 打包 uImage）
- `plat_dyn = true`（动态平台发现）
- `max_cpu_num = 8`
- features: RK3588 PCIe/XHCI/SDHCI 驱动 + Realtek RTL8125 + RKNPU

### U-Boot 运行配置

`tgoskits/os/StarryOS/configs/board/orangepi-5-plus-uboot.toml`:

- `serial = "/dev/ttyS7"`
- `baud_rate = "1500000"`
- `kernel_load_addr = "0x02000000"`（与 U-Boot `kernel_addr_r` 一致）
- `fit_load_addr = "0x0a000000"`

## 注意事项

- Docker 容器 `starryos-act-infer` 同时用于 riscv64 和 aarch64 内核编译，内有 `/opt/aarch64-linux-musl-cross` 工具链；RKNN 程序交叉编译还需 `gcc-aarch64-linux-gnu`（glibc 链接器）和 `libclang-dev`（bindgen），均已加入 `make docker-up`
- Makefile 中 `find` 已限定架构子目录（`aarch64-unknown-linux-musl` / `riscv64gc-unknown-linux-musl`），避免多架构构建时找错 uImage
- Rockchip 引导链写入时跳过 GPT 头（扇区 0~33），`dd` 使用 `skip=34 seek=34`，避免覆盖 `sfdisk` 写入的分区表

## 故障排查

### `Meet unsupported target type: 0xffffffff` → 段错误（SIGSEGV at VA 0x8）

librknnrt 在 `rknn_init` 时通过 `/dev/rknpu` 的 Action ioctl 查询 NPU 版本来判定 target type。完整崩溃链：

1. librknnrt 查 `GetHwVersion`/`GetDrvVersion` → card1 转调全局 `rknpu::action()` → `rdrive::get_one::<Rknpu>()` 返回 **None**（NPU 设备未注册）→ `NotFound`
2. librknnrt 拿不到版本 → target type 算成 `0xffffffff` → 查 target ops 表得 NULL → 解引用 `*(NULL+0x8)` → 段错误

根因总是 **NPU probe 没触发/没成功**。按以下顺序排查启动日志：

| 现象 | 原因 | 解决 |
|------|------|------|
| 日志无任何 `Rockchip NPU`/`NPU power enabled`/`NPU registered` | probe 没匹配到 FDT 节点 | DTB 用错（compatible 不匹配）→ 改用 tgoskits 的 `orangepi-5-plus.dtb`（见上"设备树"节） |
| 有 `NPU power enabled` 但无 `registered successfully` | `iomap`/`dma`/`enable_pm` 失败 | 检查 RockchipPM 电源域 (NPUTOP/NPU/NPU1/NPU2) 是否就绪 |
| `Probe failed for [Rockchip NPU]: ...` | probe 显式失败 | 按错误信息定位（reg 解析/时钟/PM） |

### `rknpu action ioctl failed: AxErrorKind::NotFound`（SetProcNice）

单独出现时是**非致命**的——只是 RKNN 运行时设置进程优先级 (nice -19) 失败，底层 `Rknpu::action(SetProcNice)` 在裸机语境本就无意义。只要版本查询能返回有效值就不影响推理。若版本查询也 NotFound，则属于上面的 target type 问题。

### 交叉链接 `cannot find -lstdc++`

容器缺 aarch64 的 C++ 交叉库。`act-infer-rknn/build.rs` **不应**链接 `-lstdc++`：动态链接 `librknnrt.so` 时，其 C++ 依赖（libstdc++.so.6 等）由 Debian rootfs 在运行时解析，链接期 ld 默认 `--allow-shlib-undefined` 不递归校验 .so 的 NEEDED。运行时 `ldd` 全部解析即可。

### rknn-toolkit2 `onnx.mapping` AttributeError

`.venv-rknn` 的 onnx 被升到 ≥1.16（`onnx.mapping` 已移除）。必须钉 `onnx==1.16.1`（见 `requirements-rknn.txt`）。

### rknn-toolkit2 `libGL.so.1 not found`

opencv-python 运行需要系统库：`sudo apt install libgl1 libglib2.0-0`。
